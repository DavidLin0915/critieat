──────────────────────────────────────
小明   豚骨拉麵 大碗          $180   加蛋
阿華   醬油拉麵               $160
小美   沾麵                   $200   不要蔥
──────────────────────────────────────

很適合 10 人的內部工具。我只建議一個小調整：**讓大家從「成員名單」選人，而不是每次手打名字。**

### 下一個問題

現在有兩個互動概念：「**提議**」（今天想吃 XX，大家 +1）和「**午餐單**」（大家填自己要點的餐）。它們的關係要怎麼設計？

### 為什麼不做獨立後台

### 建議做法：前台直接編輯

- 店家頁面右上角放「✏️ 編輯」，任何人都能改
- 清單頁放「＋ 新增店家」
- 每家店顯示「最後由 小明 於 10/8 更新」，改錯了知道找誰
- 刪除改成「隱藏」（軟刪除），不小心刪掉還能救回來

### 用你們的 Google Maps Key 讓新增變輕鬆

新增店家時，輸入店名，用 Google 的地點自動完成（Places Autocomplete）選到那家店，就能**自動帶入**地址、座標、電話、營業時間和 Google Maps 連結。同事只需要補 Google 沒有的東西：

| 欄位 | 來源 |
|---|---|
| 店名、地址、座標、電話、Google Maps 連結 | Google 自動帶入 |
| 營業時間／公休日 | Google 帶入，可以手動修正（篩選「今天有沒有開」靠這個） |
| 分類（飯、麵、便當、飲料…）、區域 | 手動選 |
| 外送連結（foodpanda、Uber Eats、你訂） | 手動貼上 |
| 菜單 | **上傳照片**或貼連結，不做成結構化品項 |

菜單用照片的原因跟午餐單一樣：維護成本最低，拍一張就好。反正點餐是自由填寫，不需要系統知道有哪些品項。

## Claude

我建議把兩種做法合在一起：**同一張卡片，分成幾個狀態**。提議和開單不是兩個獨立的東西，而是同一張卡片的不同階段，而且可以跳過提議直接開單。

### 卡片的生命週期

```
  ┌─────────┐   按「開單」   ┌─────────┐   截止/按收單   ┌─────────┐
  │ 💡 提議中 │ ───────────▶ │ 📝 點餐中 │ ─────────────▶ │ ✅ 已收單 │
  └─────────┘               └─────────┘                └─────────┘
   大家按 +1                 大家填自己的餐點            彙總清單、
                             (+1 的人自動列入，            給負責下單的人
                              只差填餐點)
       ▲
       │  有明確想法的人也可以直接從「點餐中」開始
```

- **想法還不確定**：發一個提議，「今天想吃 XX 拉麵？」，大家 +1
- **人夠了**：任何人按「開單」，卡片原地變成午餐單，剛才 +1 的人已經在名單上，只差填餐點
- **已經很確定**：直接開單，跳過提議
- **沒人附和的提議**：當天結束自動收起，不會堆積

這樣兩種習慣都照顧到了：想先問問看的人有地方問，已經決定的人不用多一道手續。而且只有一種卡片，你開發起來也單純。

| 階段 | 內容 | 說明 |
|---|---|---|
| **第一階段：午餐** | 店家資料（前台編輯、Google 自動帶入）、乾淨地圖、篩選、午餐卡（提議→點餐→收單）、身份認領 | 先把「快中午大家一起決定、一起訂」跑起來 |

| **第三階段：公車地圖** | 附近公車路線、哪些公車可以到目的地 | 需要另外串公車資料（如 TDX），獨立子專案 |
| **之後再說** | 你之後想到的新需求 | |

每個階段都走一樣的流程：HTML proto → 確認 → API／DB 實作。

**座標怎麼產生：用試算表內建的 Apps Script**

同事新增或修改地址時，試算表自動用 Google 的地址轉座標服務，把緯度、經度填進去。另外在選單加一個「重新計算座標」，萬一自動觸發失敗，可以手動補。

為什麼不在網頁打開時才轉座標？

| | Apps Script 在試算表補 | 網頁打開時才轉 |
|---|---|---|
| 呼叫次數 | 每家店只轉一次 | 每個人每次打開都要轉（可以快取，但比較複雜） |
| 費用 | Apps Script 內建服務，有免費額度，不用你們的 Key | 用你們的 Key，額度會被消耗 |
| 前端複雜度 | 讀到的資料就有座標 | 要處理轉換失敗、轉換中的狀態 |
| 好處延伸 | 同事填完就能在試算表看到座標有沒有出來，地址打錯馬上發現 | |

**你們的 Google Maps Key** 只用來顯示地圖（Maps JavaScript API）。建議在 Google Cloud 設定「HTTP 參照網址限制」，只允許你們的網域使用，避免 Key 被別人拿去用。

很多店的午餐時段是 `11:00-13:30` 或 `11:00-14:00`，下午會休息。如果判斷標準是「營業時間跟 13:00～14:00 有重疊」：

| 店家營業時間 | 判斷結果 | 實際上 |
|---|---|---|
| `11:00-14:00` | 🟢 有開 | ✅ 正確 |
| `11:00-13:30` | 🟢 有開 | ⚠️ 13:00 才訂，可能來不及 |
| `11:00-13:00` | ⚪ 沒開 | ❓ 如果 12:30 先訂好，13:00 去拿，其實可以 |

所以真正該拿來判斷的，是**你們向店家訂餐或取餐的時間**，而不是吃飯的時間。

你們通常幾點**訂餐**、幾點**拿到餐點**？

- **A.** 12:30 左右訂，13:00 左右拿到 → 午餐時段設 `12:30-13:00`
- **B.** 13:00 才開始訂，13:30 前拿到 → 設 `13:00-13:30`
- **C.** 不一定，就用 `13:00-14:00`，不準的部分自己判斷

我建議依你們實際的取餐時間來設。這個值放在設定工作表裡，之後用一陣子發現不準，改一格就好，不影響架構。

### 第 5 段：錯誤處理、部署、專案結構

**錯誤處理**

原則：**任何一部分壞掉，其他部分照常能用。**

| 狀況 | 處理方式 |
|---|---|
| 抓不到 CSV（網路問題、Google 暫時出錯） | 顯示上次成功抓到的資料（存在瀏覽器裡），並提示「資料可能不是最新的」，附「重新載入」按鈕。第一次打開就失敗時，顯示錯誤訊息加重試按鈕 |
| Google 地圖載入失敗（Key 錯誤、額度用完） | 地圖區塊顯示「地圖暫時無法使用」，**清單照常運作**，仍然可以看營業狀態、電話、外送連結 |
| 某家店還沒有座標（Apps Script 還沒跑完，或地址錯誤） | 只出現在清單，標示「地圖位置未設定」，不畫在地圖上 |
| 某家店缺少必填欄位（ID、店名） | 略過這一列，不顯示，在瀏覽器 console 留下警告訊息 |
| 營業時間格式看不懂 | 歸為「🟡 不確定」（第 4 段已定義） |
| 設定工作表缺值 | 使用程式內建的預設值（訂餐 13:00-13:30、取餐 14:00） |
