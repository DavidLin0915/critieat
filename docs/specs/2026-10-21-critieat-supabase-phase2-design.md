# CRITIEAT 正式上線第二階段（開團單＋評分共用） 設計

日期：2026-10-21　狀態：已實作並上線（2026-10-21）https://critieat.github.io/lunch.html

## 目的

第一階段（2026-10-20）上線後，同事只用網站看店家，揪團和點餐還是在 LINE 群組（使用者 2026-10-21）。
這階段把**開團單、店家評分、品項評分**從各自瀏覽器搬到 Supabase 共用，讓團隊能真的在網站上揪團點餐。

功能和畫面**照已核准的原型**，不重新設計：
- 開團單：`docs/specs/2026-10-14-critieat-lunch-card-design.md`（含 2026-10-15 歷史紀錄、「上次點什麼」）
- 點餐連品項：`docs/specs/2026-10-16-critieat-item-rating-design.md`（`menuItemId`）
- 店家評分：`docs/specs/2026-10-15-critieat-store-rating-design.md`
- 品項評分：`docs/specs/2026-10-16-critieat-item-rating-design.md`

這次只換存資料的地方，沿用第一階段的做法（`docs/specs/2026-10-20-critieat-supabase-phase1-design.md`）：`CE.supa` REST 客戶端、通關碼只擋寫入、`?demo=1` 完全不碰 Supabase。

## 決定事項

| 項目 | 決定 | 來源 |
|---|---|---|
| 範圍 | 開團單＋店家評分＋品項評分一起上 | 第一階段 spec（2026-10-20） |
| 功能與畫面 | 照原型，不重做 | 使用者 2026-10-21 |
| 即時更新 | 開團單上別人的變動（新卡片、+1、開始點餐、點餐列、收單、延後、付錢者、取消）**不用重新整理就自動出現** | 使用者 2026-10-21 |

## Claude 的決定（請在審 spec 時確認）

- **即時更新只做開團單頁**。評分（地圖店家詳情、菜單燈箱）維持重新整理後才看到別人的新評分；自己的評分存完立即更新。評分不是邊看邊等的東西。
- **即時的程度**：別人的變動幾秒內（目標 5 秒內）出現在畫面上。用 Supabase Realtime 或定時輪詢由 builder 決定，但要在免費額度內、不能讓頁面明顯變慢。分頁在背景時可以暫停，切回來立刻補抓一次。
- **即時更新不能吃掉正在打的字**：「我的餐點」編輯區還沒送出的內容、開著的建立卡片視窗、評分表單，在別人的資料更新時都要保持原樣。
- **寫入也要通關碼**：建立卡片、+1、點餐、收單、評分……所有寫入都跟第一階段一樣帶通關碼（同一個碼、同一個輸入框）。讀取不用。
- **身分＝第一階段的 `members` 表**。正式版不提供原型的「新增名字」，名單照舊由使用者在 Supabase 後台維護。選過的名字照舊記在瀏覽器。
- **刪除照原型**：取消這團＝真的刪除卡片（點餐列跟著刪）；刪除自己的點餐列、取消 +1、「刪除我的評分」（`rating-form.js`，店家與品項評分都有）也都是真刪除。第一階段「不開放刪除」的規則這裡放寬：開團單相關資料表（卡片、+1、點餐列）與兩張評分表允許刪除，但同樣要通關碼；店家、菜單仍不開放刪除。理由：原型本來就有這些刪除，而通關碼已上線。`supabase/README.md` 的「刪除一直都不開放」要跟著改寫。
- **權限檢查放前端**：誰能收單、只能改自己的列等規則（`CE.lunch.can`）照舊在前端判斷；資料庫只檢查通關碼。10 人內部工具，選名字本來就能冒充任何人，資料庫再擋沒有意義。
- **同時操作**：每個動作只改它碰到的那幾筆（例如 +1 只新增或刪除一筆 +1，送出餐點只改自己的點餐列），不要整張卡片或整份資料覆蓋，兩個人同時操作才不會互相蓋掉。同一欄位（例如兩人同時改付錢者）後存的贏。
- **以資料庫的狀態為準**：送出時如果卡片已經不在（被取消）或狀態已變（例如已收單），重新抓最新資料、顯示一行提示（例如「這團已經被取消了」），不要寫出不一致的資料。收單後改點餐列照原型允許，並正確標記「收單後修改」。
- **時間**：卡片日期、「今天」照舊以台灣時間判斷（前端算）。`createdAt` 等時間戳可用資料庫時間或前端時間，builder 決定。
- **歷史紀錄共用**：日期切換、過去卡片唯讀、「上次你點了…」都用共用資料；正式版一開始沒有歷史，不搬任何示範資料。
- **轉盤的「排除近 3 天開過團的店」在正式版恢復**（第一階段因為沒有共用團單而隱藏）。
- **第一階段為了正式版隱藏的東西全部打開**：導覽列「開團單」、店家詳情的評分區與清單上的平均分數、菜單燈箱的品項評分欄與「大家推」、已收單卡片的品項評分按鈕。示範資料與「重置示範資料」仍只在 `?demo=1`。

## 範圍

### 要做

1. **資料表**（SQL 放 `supabase/003_phase2.sql`，可重複執行，跑完需要再跑一次 `002_passcode.sql` 的話要寫清楚）：
   - 開團單：卡片、+1、點餐列（原型 spec 已預告 `cards`、`votes`、`order_items`，名稱 builder 可調）
   - `store_ratings`：同一人對同一店最多一筆
   - `item_ratings`：同一人對同一品項最多一筆，留 `storeId`、`itemName`、`itemNote` 快照（照原型）
   - 欄位照原型資料形狀，snake_case；成員欄位用名字字串（同 `members.name`）
2. **開團單改讀寫 Supabase**，加即時更新。
3. **店家評分、品項評分改讀寫 Supabase**。
4. **打開正式版的開團單與評分**，轉盤排除近期店家恢復。
5. **demo 模式不變**：`?demo=1` 全部照舊用 localStorage 與示範資料。

建議順序如上；評分和開團單可分開驗收。

### 不做

- 通知（LINE、瀏覽器推播）
- 自動收單
- 資料庫端的角色權限（誰能收單等）
- 評分的即時更新
- 管理名單的畫面、正式版新增名字
- 搬任何 localStorage 或示範資料到正式版
- Nuxt 改寫、Laravel API

### 反目標（做到了也算失敗）

- 兩個人同時操作，其中一個人的 +1 或餐點不見
- 正在打餐點時畫面被刷新，打到一半的內容消失
- 畫面顯示「已送出」但其實沒存進資料庫
- 正式網址上出現示範卡片、示範評分
- `?demo=1` 壞掉，或 demo 模式的操作寫進正式資料
- 產生費用（超出 Supabase 免費額度，例如 Realtime 連線數或請求量）

## 出錯處理

沿用第一階段與原型的提示列：

| 情況 | 處理 |
|---|---|
| 載入失敗 | 頁面上方持續提示，可重試；不顯示示範資料 |
| 寫入失敗（網路、通關碼取消） | 提示失敗，畫面維持送出前的樣子，編輯中的內容保留可再送 |
| 即時連線斷掉 | 不打擾使用者；恢復後自動補抓最新資料。斷線較久時可以顯示一行小提示 |
| 送出時卡片已被取消或狀態改變 | 重新抓資料、提示一行，見上方「以資料庫的狀態為準」 |

## 驗收

- 兩個瀏覽器（A、B）開正式網址的開團單頁、選不同名字：
  - A 建立提議 → B 不用重新整理就看到；B +1 → A 看到人數變化。
  - A 開始點餐 → A、B 同時送出各自的餐點 → 兩邊都看到兩人的餐點，沒有誰的不見。
  - B 正在打餐點時 A 送出餐點 → B 打到一半的內容還在。
  - A 收單、改付錢者、延後收單、取消這團 → B 都自動更新。
  - 收單後 B 改自己的列 → 標記「收單後修改」，A 的彙總出現提示。
- 店家評分、品項評分：A 評分後 B 重新整理看得到，平均與人數正確；同一人再評分是修改不是新增。
- 已收單卡片的品項評分、點餐連品項（`menuItemId`）、「上次你點了…」在正式版正常。
- 轉盤勾選排除近 3 天後，近 3 天開過團的店不會出現。
- 沒有通關碼不能寫入（含直接打 API）；讀取不受影響。
- `?demo=1` 一切照舊；操作後正式資料不變。
- 沿用團隊規則：不加測試框架；邏輯用 scratchpad 的一次性 node 腳本驗，UI 用瀏覽器驗（兩個瀏覽器情境可以用 headless Chrome 兩個分頁或兩個 profile）。

## 留給 builder 決定

- 資料表細部欄位、ID 產生方式、索引
- Supabase Realtime 還是輪詢；要不要因此引入 Supabase JS client（CDN 固定版本）
- `CE.lunchStore`、`CE.ratingStore` 等的非同步改寫方式（第一階段是「啟動時載入記憶體、讀取同步、寫入非同步」，可沿用）
- 原型 `lunch.js` 的「舊陣列 → 新陣列」純邏輯怎麼對應到逐筆寫入（可保留純邏輯做檢查與計算，另外產生要寫入的差異）
